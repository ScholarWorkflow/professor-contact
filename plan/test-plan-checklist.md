# 测试计划自检清单

本清单是提交测试计划审核前的固定自检，用于避免同一类问题在多个 PR 上重复出现。每条都对应一次实际被审出的问题，写测试计划时逐条核对，并在计划的“自检”小节里声明已核对。

## 1. 必测项只覆盖本批直接改变的行为

- 每个编号只引用能证明本批行为的方法；不整模块运行，不把同文件的无关用例、旧合同检查或既往缺陷的回归用例设成本批通过条件。
- 引用既有用例时写清“模块.类.方法”；只能按模块运行时，说明该模块的全部用例都落在本批范围内（例如模块本身只有 2 个用例）。
- 收窄后要能把这些入口映射回此前执行日志的具体行；多出的行只作诊断，不写进通过条件。

## 2. 仓库持续集成不属于业务必测项

- 全量 `unittest discover` 作为“既有仓库检查”单独引用（运行编号、所跑 head、检查状态），不占必测编号、不写“全量通过”为业务目标。
- 合并要求照常执行，不因本批扩张或缩减。

## 3. 每个临时脚本都有取得步骤

- 计划里出现的每个脚本（对比脚本、驱动、夹具）都要写明确切来源路径与 `cp`/移动命令；不能只写“见下节要点”。
- 来源缺失时的处理是“按执行记录找回同一脚本，仍找不到就停止并交计划所有人”，不允许凭提纲临时改写正式比较方法。

## 4. 命令块启用 `set -e`

- 多步比较前必须先确保每步成功：两条驱动命令都失败、输出都为空时，`diff` 依然会成功并打印“相同”。
- 每个 `sh` 代码块以 `set -e` 开头；预期结果里写明“所有前置命令退出 0”。

## 5. 失败注入要到达目标分支

- 写清注入点在第几次调用、此时事务处于哪一步、失败后断言哪几个文件回到什么内容。
- 需要证明“部分安装后回滚”时，注入点必须在首个文件**完成安装**之后（例如两个目标都预先存在时对 `atomic_json_many` 注入第四次 `os.replace`，对 `staged_pair_commit` 注入第二次）。
- 只到一个未完成的中间状态（如备份已做、安装未做）不能证明回滚。

## 6. 计划与记录同一套口径

- 计划里的命令、标签、预期输出要与执行记录逐字对齐；标签变了就同步计划。
- 记录里的表格行与结论行引用同一来源；`/tmp` 产物点名到文件，不用通配目录。
- 失败与修正尝试保留，不用后续成功覆盖先前失败。

## 7. 编号与版本一致

- 增删必测编号时同步修订记录、审核状态与执行记录里的编号。
- 计划指针（对应执行计划版本、测试计划版本）与实际文件版本一致。
