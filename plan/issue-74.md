## 方案

新增 `tests/runtime/fixture_support.py`，只提供以下共用能力：

- 解析并检查样例根目录是否位于生产者检出目录之外；
- 拒绝非目录和非空目录；已有空目录保持原样，缺失目录按需创建；
- 第 53 号保留原有的“两根目录不能完全相同”检查，不增加“互为祖先即拒绝”的限制；
- 检查清单输出位于生产者检出目录之外、目标尚不存在，并且不与本次已知样例文件路径相同；
- 提供保持既有格式的文本和 JSON 写入；
- 清单使用排他创建，目标出现时拒绝覆盖；
- 提供文件 SHA-256 计算；
- 记录目录是否由本次调用创建及准备时的文件系统身份，只用于第 53 号失败回滚时避免删除错误目录。

第 53、55 号入口继续负责各自的业务数据、文件布局、清单字段和返回对象。共用模块不包含议题专属业务断言，也不负责为不同运行分配目录。

### 跨运行目录的唯一责任方

跨运行目录分配的唯一责任方是**测试执行层**。

每次正式测试执行开始前，测试执行层创建一个本次运行独占的 `<run-root>`。不同运行必须使用不同的 `<run-root>`；本次运行结束后的生命周期与清理由测试执行层负责。第 53、55 号准备入口只消费测试执行层传入的路径，不持有跨运行占用状态，不自行生成 run id，也不负责判断另一次运行正在使用什么目录。

正式测试执行采用以下目录用途：

第 53 号：

```text
<run-root>/
  consumer/               -> 传给现有 --program-root
  profile/                -> 传给现有 --profile-root
  output/
    fixture-manifest.json -> 传给现有 --output
```

第 55 号：

```text
<run-root>/
  consumer/               -> 传给现有 --program-root
  output/
    fixture-manifest.json -> 传给现有 --output
```

这里的目录结构约束的是**正式测试执行如何分配路径**，不改变两个准备脚本的公开参数。共用工具不要求所有调用者必须使用这些目录名，也不因为合法路径存在父子关系就拒绝；它只执行 R3 已授权的安全检查和第 53 号原有的“两根完全相同”检查。

### 方案选择与替代方向

采用“测试执行层分配 `<run-root>`，既有准备入口消费其下固定用途路径”的方案，原因是：

- 不改变第 53、55 号现有命令参数和返回对象；
- 跨运行独占责任只有一个 owner；
- 输入、资料与输出在一次运行下有固定位置，清理范围明确；
- 共用工具保持无跨运行状态，只处理单次调用的目录安全和写入。

现实替代方向是让 `fixture_support.py` 自己创建 `<run-root>`、分配子目录并把这些路径返回给调用方。该方向不采用，因为它会把目录生命周期和跨运行占用责任转移到共用工具，并要求改变现有调用方式或返回 contract；这超出 R2 要求的兼容范围，也没有必要。

## 写入与兼容要求

R2 的兼容范围覆盖既有允许的调用：

- 原命令参数不变；
- 返回对象和错误通道不变；
- 成功生成的文件内容和 JSON 格式不变；
- SHA-256 摘要算法不变；
- 第 53、55 号既有业务验收要求不变；
- 直接执行脚本和按文件路径加载模块两种调用方式继续可用；
- 第 53 号继续拒绝两个根目录完全相同，不新增祖先/子孙关系的一刀切拒绝。

按 R3 拒绝以下输入：

- 样例根目录位于生产者检出目录或其子目录；
- 样例根目录是普通文件或其他非目录对象；
- 样例根目录已有内容；
- 清单输出位于生产者检出目录或其子目录；
- 清单输出已经存在；
- 清单输出与本次已知样例文件路径相同。

预先能发现的非法输入在写入样例前失败。清单实际创建时再次使用排他创建；如果目标在此前出现，则拒绝覆盖，已经生成的样例保留用于诊断。

正式测试执行另外满足：每次运行先取得独占 `<run-root>`，并按上一节的固定用途把 `consumer`、`profile` 和 `output` 路径传给既有入口。该执行约定负责满足“不同运行使用独立目录”，不把跨运行分配逻辑塞进共用工具。

## 第 53 号目录回滚

第 53 号依次准备程序根和资料根。

- 第一个根目录原本存在且为空：保持原目录；第二个根目录准备失败时不删除第一个目录。
- 第一个根目录由本次调用创建：第二个根目录准备失败时，仅当文件系统身份仍与准备时一致才删除第一个目录。
- 身份已经变化：停止删除并返回错误，避免删除后来替换到同一路径的目录。
- 两个根目录都准备完成后，后续写入失败保留已写出的部分样例，不做递归清理。
- 不用“禁止父子路径”代替回滚边界。回滚只删除能够证明由本次调用创建且身份未变化的目录。

## 影响

- intended_change：第 53、55 号准备入口共享目录准备、文件写入和摘要代码；补上 R3 要求的已有内容与清单覆盖保护；正式测试执行统一采用每次运行独占 `<run-root>` 的目录安排。
- preserved_behavior：既有允许调用的参数、返回对象、错误类型、业务文件内容、摘要、清单字段和两种调用方式；第 53 号只保留原有的“两根完全相同”拒绝，不新增祖先关系禁令。
- approved_behavior_change：只包含 R3 明确授权的危险目标拒绝、已有内容保护和清单防覆盖。
- prohibited_side_effect：读取真实用户资料、覆盖已有内容、删除调用前已有目录、修改业务程序、启动外部服务、改变产品失败判定、让共用工具持有跨运行状态、把测试目录命名升级成产品接口要求。
- 产品数据迁移：不适用。

## 关键安全条件与反例

必须一直成立的条件：

1. 不同正式测试运行的可写内容位于不同 `<run-root>`。
2. 单次运行的 `consumer`、`profile`、`output` 用途明确，清理本次 `<run-root>` 不影响其他运行。
3. 共用工具拒绝 R3 明确禁止的目标，不覆盖已有文件。
4. 共用工具不为了简化实现而新增正式需求未授权的路径关系限制。
5. 第 53 号失败回滚只删除能够证明由本次调用创建且身份未变化的目录。

代表性反例：

- 两次运行被分配到同一个 `<run-root>`：由测试执行层在调用准备入口前阻断，不能依赖共用工具猜测另一次运行状态。
- `program_root` 与 `profile_root` 完全相同：保持目标版本原有失败行为。
- `profile_root` 位于 `program_root` 下，但没有触犯 R3 其他禁止条件：不能仅因父子关系新增失败；正式测试执行本身使用固定的 sibling 布局，不需要靠该禁令取得隔离。
- 清单路径在准备后、写入前被其他进程创建：排他创建拒绝覆盖，已生成样例保留用于诊断。
- 第 53 号第一个目录由本次创建后被替换：身份不一致时停止删除并返回错误。
